# Changelog

Формат версии: `X.YY.ZZZ`. Патч (`ZZZ`) увеличивается на 1 при каждой доработке; старшие номера (`X`, `YY`) меняются только по явной команде пользователя.

## 1.00.049 — реально исправлена прослушка каналов с «/» в названии (1.00.048 чинил не тот механизм)

- Фикс 1.00.048 (catch-all маршрут) исходил из неверной посылки: что Kestrel декодирует `%2F` обратно в буквальный `/` перед маршрутизацией, из-за чего однопараметрический маршрут не мог совпасть. Проверено эмпирически (временный debug-эндпоинт, эхо сырого значения параметра): всё было ровно наоборот — ASP.NET Core **намеренно не декодирует** `%2F`/`%5C` при связывании значения параметра маршрута (защита от path-traversal-неоднозначности для маршрутов, строящих файловые пути из параметров). Поэтому в `AudioStreamEndpoint.StreamAsync` реально приходила строка вида `Studio21 Y401 mp3%2F96k` (с буквальными тремя символами `%`, `2`, `F`) — она не совпадала с настоящим именем канала в словаре запущенных движков (`AudioEngineManager._engines`, ключ — `Studio21 Y401 mp3/96k`), `SubscribeAudio` возвращал `null`, и метод молча отдавал собственный 404 — без единой строки в лог (эта ветка `reader is null` изначально не логировалась). Catch-all-маршрут из 1.00.048 был безобидным, но не решал настоящую проблему.
- Реальное исправление — одна строка в `Services/AudioStreamEndpoint.cs`: `channelName = Uri.UnescapeDataString(channelName);` в начале `StreamAsync`, до использования значения для поиска канала. Здесь это безопасно — `channelName` используется только как ключ поиска в словаре уже запущенных каналов в памяти, не для построения файлового пути, так что риска path traversal нет.
- Обнаружено благодаря присланным пользователем HAR-подобным данным (URL из DevTools Network, `%2F` в пути) и вопросу «нужно ли экранировать другие символы» — это натолкнуло на мысль перепроверить, что именно долетает до сервера, вместо дальнейших предположений. Подтверждено воспроизведением на тестовом канале с реальным именем-с-слэшем (`source.type: stream` на заведомо недоступный URL, `auto_start: true`, чтобы движок гарантированно появился в `_engines`): до фикса — `404 Not Found`, после — запрос корректно зависает в ожидании данных (как и должно быть для источника без реального звука) вместо мгновенного 404.

- Найдена причина бага из 1.00.047 благодаря присланному логу с продакшн-сервера: у ВСЕХ каналов там название содержит «/» как часть суффикса формата — «Studio21 Y401 mp3/96k», «Retro FM-HQ wav/PCM» и т.п. Браузер корректно кодирует это в URL (`Uri.EscapeDataString` → `%2F`), но ASP.NET Core/Kestrel декодирует `%2F` обратно в буквальный «/» в `HttpContext.Request.Path` ДО маршрутизации — однопараметрический маршрут `{channelName}` не может совпасть через этот декодированный слэш, и запрос молча проваливался в `MapFallbackToPage` (SPA-страница вместо аудиопотока). Браузерный `<audio>` получал HTML вместо MP3 и мгновенно падал с ошибкой — без единой записи в лог, поскольку `AudioStreamEndpoint.StreamAsync` вообще не вызывался. Не зависело от типа источника — просто в этом развёртывании все AoIP-каналы (звуковая карта/Livewire) исторически называются с «/», а работавшие Icecast/HLS-каналы, видимо, без него.
- `Program.cs`: маршрут `/api/playback/stream/{channelName}` заменён на catch-all `/api/playback/stream/{*channelName}`, который забирает остаток пути as-is, включая декодированные слэши. Клиентский код (`MainLayout.razor`) не менялся — кодирование URL там уже было верным.
- Диагностика из 1.00.047 (логи прогрева `PlayoutBuffer`, сторож «буфер не наполнился», эскалация stderr) остаётся в коде — полезна для будущих похожих проблем.
- Проверено вживую: `curl` на URL с `%2F` в названии канала — раньше маршрут не совпадал бы вовсе (SPA-страница, `Content-Type: text/html`), теперь возвращает корректный `404 Not Found` от `AudioStreamEndpoint.StreamAsync` (для несуществующего в тестовом конфиге канала — именно то поведение, которое означает «маршрут дошёл до обработчика»); обычные названия без «/» продолжают работать как раньше.

## 1.00.047 — диагностика: прослушка звуковой карты/Livewire не даёт звука

- Пока не найдена причина (статический разбор кода не выявил разницы в серверном конвейере между источниками — прослушка использует один и тот же класс `PlayoutBuffer`/`AudioStreamEndpoint` независимо от типа источника, а сама запись на диск для этих каналов подтверждённо работает нормально). Добавлена диагностика вместо слепого исправления:
  - `PlayoutBuffer`: теперь пишет в лог (Information), когда буфер прогрелся, и включает имя канала в предупреждение о паузе в поступлении чанков (раньше имя канала не попадало в этот лог вообще, хотя поле для него было).
  - `AudioStreamEndpoint` (ffmpeg-кодирование MP3 для браузера): добавлены отсутствовавшие `-hide_banner -loglevel error` (были только у остальных вызовов ffmpeg в проекте); буферизуется stderr и логируется на уровне Warning, если ffmpeg-процесс кодирования завершился сам, раньше отключения клиента; новый «сторожевой» лог — если буфер не прогрелся за `задержка+3`с, пишется Warning о том, что от захвата не пришло ни одного чанка для этого прослушивания.
  - Оба новых предупреждения видны при уровне логирования по умолчанию (INFO), не требуют включения DEBUG.

- Процент занятого места от прогноза (вкладка «Выход» в редактировании канала, добавлено в 1.00.045) округляется до 2 знаков после запятой (`"F2"`) вместо произвольного числа знаков.

## 1.00.045 — права администратора, монитор ресурсов, прогноз занятого места на диске

- **Права администратора**: `is_admin`/`admin_groups` (уже существовали в `users.yaml`/`ldap.yaml`, но раньше ни на что не влияли) теперь реально ограничивают интерфейс. Пока авторизация вообще не настроена — поведение как раньше, без ограничений. Когда включена и вошедший пользователь не администратор: скрыты пункты бургер-меню «Новый канал», «Запустить/остановить запись всех», «Массовое изменение», «Обновить конфигурацию», «Настройки», «Монитор ресурсов», а на карточках каналов — кнопки старт/стоп записи, «Редактировать», «Клонировать», «Удалить». Прослушивание (▶) и индикаторы (📊) остаются доступны всем. `CurrentUserContext.CanManage` — новый общий гейт (`!AuthRequired || IsAdmin`), проверяется и в разметке (скрытие кнопок), и внутри самих обработчиков (защита от повторного клика/гонки, а не только косметика).
- **📈 Монитор ресурсов** (новый пункт бургер-меню, только для администраторов): диалог с автообновляемой раз в 2 секунды таблицей ЦП%/памяти по основному процессу и по каждому ffmpeg-подпроцессу каждого запущенного канала (отдельно захват и запись файла). Процессы отслеживаются по PID, которые уже держат `StreamCapture`/`LivewireCapture`/`AudioWriter` — без WMI и без сканирования дерева процессов ОС.
- **Прогноз объёма на диске** (вкладка «Выход» в редактировании канала): горизонтальный индикатор — сколько места займут записи при текущем битрейте/формате и сроке хранения, и сколько из этого уже занято в папке сохранения сейчас (% и ГБ). Новый `Services/DiskUsageEstimator.cs` (чистая логика, покрыта тестами) + асинхронный рекурсивный подсчёт объёма папки с таймаутом (как у проверки пути сохранения), запускается один раз при первом открытии вкладки и по кнопке «Обновить».

## 1.00.043 — детектор тишины теперь по-настоящему сохраняет файл и открывает новый при возобновлении

- Реализация из 1.00.041 держала ffmpeg-процесс и файл открытыми на всё время тишины, только приостанавливая запись в stdin — на проде это означало, что при затяжной тишине файл фактически не сохранялся до следующей плановой ротации или полной остановки канала.
- Теперь: на подтверждённой тишине текущий файл закрывается и сохраняется немедленно; на подтверждённом возобновлении звука открывается НОВЫЙ файл, чьи имя и содержимое отсчитываются от момента `resume_seconds` до фактического физического возврата звука (буферизованное в памяти окно дозаписывается в начало нового файла, затем идёт живой звук).
- `AudioWriterPauseResumeTests.cs` переписан под проверку двух файлов вместо одного.

## 1.00.042 — фильтр «Статус:» на главной получил значение «Тишина»

- Кнопка «Статус:» (`Index.razor`) теперь циклится Все → Запущенные → Остановленные → Ошибка → **Тишина** → снова Все. «Тишина» фильтрует по тому же `EngineStatus.IsSilent`, что красит «Звук»-индикатор на карточке (не путать с самим статусом записи) — реализовано отдельным page-local enum `StatusFilterOption`, не смешанным с `ChannelRunState`, которым по-прежнему красится точка статуса записи. Новый янтарный тон кнопки (`filter-state-silent`) отличает это состояние от красной «Ошибка».

## 1.00.041 — детектор тишины теперь реально останавливает и возобновляет запись

- Раньше детектор тишины только красил индикатор «звук/тишина» на карточке канала — запись в файл никогда не приостанавливалась. Теперь по умолчанию: после `trigger_seconds` непрерывной тишины запись в текущий файл приостанавливается (ffmpeg-процесс и файл не закрываются — ротация по длительности продолжает работать), а после `resume_seconds` непрерывного звука возобновляется, с дозаписью буферизованного в памяти звука за `2 * resume_seconds` до момента подтверждения — то есть с запасом `resume_seconds` ПЕРЕД фактическим физическим возвращением звука, а не только перед моментом, когда детектор его подтвердил, чтобы не терять начало передачи/музыки из-за задержки на подтверждение детектора.
- Новая опция «Не останавливать запись при тишине» (`silence_detector.dont_stop_recording`, выключена по умолчанию) на вкладке «Детектор тишины» и в «Массовом изменении» — отключает управление записью, оставляя только индикацию.
- Новый `Audio/BackfillBuffer.cs` (кольцевой буфер, ограниченный длительностью, а не числом чанков) и `AudioWriter.SetRecordingActive(bool)`. Покрыто тестами: `BackfillBufferTests.cs` и сквозной `AudioWriterPauseResumeTests.cs` (реальный `ffmpeg.exe`, реальный WAV-файл, побайтовая проверка итоговой последовательности звука).

## 1.00.038 — документация: права NTFS при копировании на сервер под другой учётной записью

- В `README.md`/`HOWTO.md` добавлено предупреждение: если файлы на сервер копирует одна учётная запись, а служба/приложение запускается под другой, унаследованные права на `config\`/`log\` могут не дать этой учётной записи писать в свои же файлы (даже будучи локальным администратором — UAC отфильтровывает эту группу из токена не-elevated-сессии). Реальный случай: `settings.yaml` не сохранялся с `UnauthorizedAccessException`, при этом `icacls` на папке выглядел нормально. Исправляется явной выдачей прав (`icacls ... /grant ... /T`) либо запуском как служба Windows (`LocalSystem` имеет полный доступ к локальным файлам без этой возни).

## 1.00.037 — запись больше не теряет несколько секунд звука при совпадении имени файла

- `AudioWriter` запускал ffmpeg без флага `-y`. Если целевой файл вывода уже существовал на диске (например, осиротевший процесс ffmpeg от предыдущего некорректно завершённого запуска ещё держал файл с тем же посекундным именем), ffmpeg не может спросить подтверждение перезаписи (stdin здесь — канал с сырым PCM, не терминал) и просто завершается сразу с «File already exists. Exiting.» — это ронялось в лог как ERROR («Ошибка записи в stdin ffmpeg», «Процесс вывода ffmpeg завершился через 0.1 с») и стоило ~5 секунд записи каждый канал, где это происходило (реальный случай — сразу после перезапуска приложения на боевой машине).
- Теперь ffmpeg всегда вызывается с `-y`: имя файла всегда строится из текущей метки времени, так что совпадение имени означает только устаревшие/неполные данные от прерванного процесса — их можно спокойно перезаписать, не жертвуя непрерывностью записи.

## 1.00.036 — LWRP больше не выдумывает несуществующие Livewire-каналы (1-216, 239 и т.п.)

- Причина возвращения «фантомных» каналов после фикса 1.00.030: тот фикс лишь перестал засчитывать автосгенерированные placeholder-имена вида «SRC 1»/«PC 12» как настоящее имя канала — но `LivewireDiscoveryService.EnrichNamesViaLwrpAsync` по-прежнему создавал СОВЕРШЕННО НОВУЮ запись канала на основе одного лишь ответа LWRP `SRC`, даже если этот номер канала ни разу не встречался в реальном Advertisement-трафике узла. LWRP-таблица «известных источников» узла не обязана совпадать с тем, что он физически порождает (см. `LIVEWIRE.md` §3) — например, у одного PC-логгера в таблице SRC оказалось 200+ номеров, часть из которых даже носила правдоподобные названия реальных станций («RR-intelsat», «R7-Yamal401» и т.п.), оставшиеся в его локальной конфигурации, хотя реально эти каналы этим узлом не транслируются.
- LWRP теперь может только ДОЗАПОЛНИТЬ имя для канала, который уже подтверждён настоящим Advertisement-пакетом от его собственного устройства — никогда не создаёт канал с нуля. Поле `RTPE` (включён/выключен источник) намеренно не используется как признак фантомного канала — в реальных данных оно равно 0 даже у заведомо настоящих, работающих каналов, так что не является надёжным индикатором.
- **Важно**: этот фикс останавливает появление НОВЫХ фантомных записей, но уже накопленные в `config/livewire.yaml` (в том числе снова, после 1.00.030) нужно почистить вручную ещё раз — удалить файл или отредактировать — и один раз переподключить Livewire.

## 1.00.035 — метаданные HLS больше не умирают навсегда после неудачного старта

- Причина многочасовых пропаданий метаданных (например, у Capital FM — метаданные не появлялись 2.5 часа, пока канал не был перезапущен вручную): `HlsMetadataReader` — одноразовая задача. Если при старте канала известный URL метаданных (единственный работающий вариант для станций, чей JSON-эндпоинт живёт на другом хосте, чем плейлист) не ответил, автоопределение JSON тоже не нашло эндпоинт, а резервный разбор ID3 через ffprobe тоже не дал результата — задача просто завершалась НАВСЕГДА, и ничто в приложении её не перезапускало до полной перезагрузки конфигурации канала.
- Проверка известного URL при старте теперь повторяется несколько раз (как уже делало автоопределение), а если ничего не найдено — читатель не завершается, а продолжает периодические попытки поиска JSON в фоне (раз в 2 минуты) до конца сессии канала, самостоятельно восстанавливаясь без ручного перезапуска. Разбор ID3 остаётся одноразовым, как и было.

## 1.00.034 — исправлен фикс из 1.00.033: удалённая служба реально находится и управляется

- Живой прогон 1.00.033 на реальном сетевом пути показал «служба не найдена», хотя она работала. Причины (обе подтверждены вживую): `Resolve-Path` для UNC-пути возвращал строку с префиксом провайдера (`Microsoft.PowerShell.Core\FileSystem::\\...`), ломавшую определение удалённого компьютера — заменено на `.ProviderPath` (чистый путь); и `Get-Service -ComputerName` вообще отсутствует в PowerShell 7/Core (только в Windows PowerShell 5.1), а скрипт может выполняться в любом из двух движков.
- Опрос и управление службой при удалённом сценарии переведены на CIM/WMI (`Get-CimInstance`/`Invoke-CimMethod` на `Win32_Service`) вместо смеси `Get-Service -ComputerName`/`sc.exe` — работает одинаково в обеих версиях PowerShell и не зависит от локали Windows на удалённой машине (в отличие от текстового вывода `sc.exe query`).

## 1.00.031 — правильный номер канала LWRP (RTPA, не ведущий индекс); человекочитаемый `last_seen`

- Найденные Livewire-каналы могли показываться под неверными (заниженными) номерами — например, реальные каналы 6501-6516 отображались как 1-16. Причина: ведущий `<индекс>` в ответе LWRP на команду `SRC` — не всегда настоящий номер канала, а на некоторых узлах просто локальная позиция источника на самом устройстве; настоящий номер корректно закодирован в поле `RTPA` той же строки, которое раньше не читалось вовсе. `LwrpParser.ParseSourceNames` теперь берёт номер канала из `RTPA`, а не из ведущего индекса (откат на индекс — только если `RTPA` в строке отсутствует).
- `last_seen` в `config/livewire.yaml` теперь человекочитаемый (`YYYY-MM-DD hh:mm:ss`, локальное время) вместо Unix-секунд — старые числовые значения по-прежнему читаются без ошибок при загрузке уже существующего файла.

## 1.00.030 — исправлены ложные каналы 1-216 в списке обнаруженных Livewire-источников

- Список «Найденных каналов» Livewire мог показывать сотни несуществующих записей вида `SRC 1`, `PC 12` и т.п. Причина — не в расчёте мультикаст-адреса (проверено, ошибки нет), а в том, что таблица `SRC`, отдаваемая узлом по LWRP, не обязана совпадать с тем, что узел физически порождает (документированная особенность протокола, см. `LIVEWIRE.md` §3) — конкретный узел пользователя вернул 216 слотов, большинство из которых никогда не переименовывались и подставляют шаблонное имя вида `"<префикс> <номер слота>"` вместо пустого.
- `LwrpParser.ParseSourceNames` теперь отбрасывает такие шаблонные имена (непустой префикс + хвостовые цифры, точно равные номеру этой же строки `SRC`), сохраняя реальные имена, даже если они тоже оканчиваются на цифры, не совпадающие с номером слота (например, `R7-Yamal401` на слоте 10). Затрагивает только путь LWRP-дозаполнения; обнаружение через Advertisement не изменилось.
- Это останавливает появление НОВЫХ ложных записей; уже накопленные записи в `config/livewire.yaml` нужно почистить вручную (удалить файл или отредактировать) и один раз переподключить/перезапустить Livewire — подробности в `docs/HISTORY.md` #129.

## 1.00.028 — source-aware задержка буфера индикаторов (ветка `fix/indicators`)

- Буфер индикаторов/прослушки (`PlayoutBuffer`) больше не использует одну общую задержку 12с для всех каналов: периодическая пауза, ради которой этот запас существует, исторически наблюдалась только у HLS-источников (ожидание следующего live-сегмента), никогда у Icecast/звуковой карты/Livewire.
- Non-HLS каналы (Icecast, звуковая карта, Livewire) теперь используют небольшую фиксированную задержку — новый дефолт настройки «Задержка буфера индикаторов» снижен с 12с до **2с** (достаточный запас на обычный сетевой/системный джиттер). **Важно для существующих инсталляций**: значение из уже сохранённого `app.yaml` не мигрируется автоматически — старое значение 12с (или любое, установленное вручную) сохранится до тех пор, пока настройки не будут пересохранены на вкладке «Индикаторы».
- HLS-каналы теперь сами измеряют реальную длительность сегмента из собственного плейлиста (`#EXT-X-TARGETDURATION`, с переходом к нужному варианту у мастер-плейлиста) и подбирают буфер как `длительность + 2с` (в диапазоне 4-30с), вместо одной константы на все HLS-каналы независимо от их реального сегментного темпа. Измерение — фоновое и не блокирующее; до первого успешного измерения (и при любой ошибке — сеть, парсинг, таймаут) канал использует прежнюю проверенную константу 12с.
- Новые `Audio/HlsPlaylistParser.cs` и `Audio/HlsSegmentDurationService.cs`; `AudioEngineManager.GetPlayoutBufferSeconds(channelName)` и `AudioStreamEndpoint` используют фактически применённую для канала задержку, чтобы прослушка в браузере и индикатор оставались синхронны.

## 1.00.026 — настоящая причина потери параметров в `Update-Quince.ps1`: ручное экранирование при UAC-relaunch

- Прошлый фикс (1.00.025, порядок Resolve-Path/повышение прав) не покрывал главный случай: `Start-Process -ArgumentList` просто склеивает элементы массива через пробел, а ручные кавычки вокруг значений (`"$value"`) ломаются, если путь оканчивается на `\` — `\"` перед следующим токеном читается Windows как экранированная (не закрывающая) кавычка, и весь остаток командной строки (включая соседний параметр, например `-CopyConfig`) утекает внутрь значения предыдущего. Воспроизведено и подтверждено на пути с завершающим `\`.
- Relaunch переписан на `System.Diagnostics.ProcessStartInfo.ArgumentList` — экранирование каждого аргумента (включая завершающий `\`) делает сам .NET, ручных кавычек в коде больше нет. Проверено тем же путём с завершающим `\` — параметр и переключатель передаются корректно.

## 1.00.025 — исправлена потеря параметров при повышении прав в `Update-Quince.ps1`

- Относительные `-InstallPath`/`-SourcePath` теперь резолвятся в абсолютные ДО перезапуска с UAC-запросом, а не после: `Start-Process -Verb RunAs` на обычном рабочем столе часто сбрасывает рабочую директорию elevated-процесса (например, на `System32`), из-за чего относительный путь, отложенный до повышения прав, резолвился не туда — выглядело так, будто параметры вообще не передаются.
- Перезапуск теперь через исполняемый файл текущего хоста (`(Get-Process -Id $PID).Path`), а не жёстко зашитый `pwsh.exe` — раньше это ломалось на машинах без установленного PowerShell 7. Добавлен явный `-WorkingDirectory` для elevated-процесса.

## 0.00.072 — вкладка браузера больше не застревает на «Reconnecting…» после простоя

- **Причина**: `AddServerSideBlazor()` вызывался без опций — `CircuitOptions.DisconnectedCircuitRetentionPeriod` (3 минуты по умолчанию) и SignalR `ClientTimeoutInterval` (30 секунд) рассчитаны на активно открытую вкладку; фоновая/неактивная вкладка (браузер придерживает JS-таймеры), сон ноутбука или короткий сетевой сбой легко превышают эти пороги — сервер выбрасывает состояние circuit, и штатный клиентский реконнект `blazor.server.js` (небольшое фиксированное число попыток на коротком таймере) исчерпывается впустую, оставляя пользователя на баннере «Reconnecting…» до ручного обновления страницы.
- `Program.cs`: `AddServerSideBlazor` — `DisconnectedCircuitRetentionPeriod` поднят до 15 минут; `AddHubOptions` — `ClientTimeoutInterval` 60с/`KeepAliveInterval` 15с (требование SignalR: таймаут ≥ 2×keep-alive) — больше запаса на задержку пингов от придержанной браузером фоновой вкладки.
- `Pages/_Host.cshtml`: `blazor.server.js` переведён на `autostart="false"`; добавлен явный `<div id="components-reconnect-modal">` (стандартный паттерн Blazor для управления UI переподключения) и новый `wwwroot/reconnect.js` — ручной `Blazor.start()` с увеличенным окном повторных попыток (30 попыток × 3с ≈ 90с вместо короткого дефолта), плюс `MutationObserver` на классы `components-reconnect-failed`/`-rejected`: как только весь ресурс попыток исчерпан или сервер явно отверг старый circuit (та самая ситуация «уже нечего восстанавливать»), страница сама перезагружается — вместо баннера, который никто не заметит. `app.css` — минимальное тематическое оформление баннера (fixed, по центру сверху, цвета из палитры темы).
- Проверено вживую (Playwright, самодостаточный тест — сам поднимает и убивает процесс `Quince.Service.exe`): убийство процесса сервера показывает баннер «⚠️ Переподключение к серверу…» в течение 1с; повторный запуск сервера (новый процесс — старый circuit гарантированно недействителен) приводит к автоматической перезагрузке страницы и полному восстановлению интерактивности в течение 1с после того, как сервер снова стал доступен — без единого ручного действия.

## 0.00.071 — ручной «Старт» после исчерпания лимита переподключений снова реально работает

- **`AudioEngineManager.Start()` молча ничего не делал для канала, остановившегося по исчерпанию лимита переподключений** (`EngineStatus.HasError`): `OnReconnectExhausted` останавливает `ChannelEngine` напрямую, минуя `AudioEngineManager.Stop()`, поэтому запись о канале оставалась в внутреннем `_engines` — а `Start()` при виде уже существующей записи просто выходил (`if (_engines.ContainsKey(...)) return;`), не создавая новый цикл подключения. Клик «Старт» на карточке с красной рамкой не делал вообще ничего.
- Тот же баг был и в `IsRunning()` (просто `ContainsKey`, без проверки реального статуса) — из-за него «Запустить запись всех каналов» тоже молча пропускал каналы в состоянии ошибки, а автостарт прослушки (`AudioPlaybackService`) не мог поднять такой канал даже для ▶.
- Оба метода переведены на проверку `engine.Status.IsRecording` вместо одного факта присутствия в словаре; `Start()` при обнаружении «мёртвой» записи убирает её и создаёт канал заново — обычным путём, тем же, что и любой холодный старт.
- Проверено вживую (Playwright + разбор лог-файла): канал с заведомо недоступным адресом дошёл до `HasError`, ручной «Старт» тут же запустил новый цикл подключения («попытка 0» в логе сразу после клика) — рамка карточки перестала быть красной, статус-точка вернулась в «Запись идёт».

## 0.00.033 — прослушивание канала теперь играет в браузере, а не на сервере

- **Архитектурное исправление**: кнопка ▶ «Прослушать канал» раньше воспроизводила звук через NAudio/WASAPI на звуковую карту **сервера** (машины, где выполняется `Quince.Service.exe`) — при удалённом доступе оператор с другого компьютера ничего не слышал у себя. Теперь сервер кодирует живой поток канала в MP3 через бандлированный `ffmpeg.exe` и отдаёт его новым HTTP-эндпоинтом (`GET /api/playback/stream/{канал}`) скрытому `<audio>`-элементу на странице — звук играет через аудиовыход **того компьютера, где открыт браузер**, тем же способом, что и обычное веб-аудио.
- Выбор конкретного устройства воспроизведения на компьютере оператора пока недоступен и отложен в бэклог: `HTMLMediaElement.setSinkId()` браузеры разрешают только в secure context (HTTPS или `localhost`), а приложение сейчас слушает обычный HTTP для доступа по сети. Пока используется устройство по умолчанию в ОС/браузере оператора.
- Убрана настройка «Аудиовыход для прослушивания» из диалога «Настройки приложения» и поле `output_device_uid` из `app.yaml` — они управляли звуковым устройством **сервера**, что для нового клиент-стороннего воспроизведения не имеет смысла. Соответствующий код (`AudioPlaybackService.EnumerateDevices`/`ResolveOutputDevice`, NAudio `WasapiOut`) удалён.
- Аудиовходы (запись с потоков/звуковой карты) не затронуты — это по-прежнему корректно происходит на сервере, где реально находится записываемое оборудование/потоки.

## 0.00.021 — индикатор метаданных, ускорение старта HLS-прослушивания, прослушивание остановленных каналов

- **Индикатор «тишины» на карточке канала переосмыслен как индикатор здоровья метаданных.** Раньше это была грубая оценка «есть ли сейчас сигнал» по мгновенному True Peak (порог -50 дБ) — независимая от статуса записи, из-за чего при остановленной записи (уровень сбрасывается в -∞) индикатор всегда показывал красный, что вводило в заблуждение. Теперь: серый — если запись не идёт; красный — только если для канала настроена ссылка на метаданные, но они не определяются (после 30-секундного периода ожидания, покрывающего худший случай HLS-обнаружения с повторными попытками); зелёный — иначе (в том числе если метаданные вообще не настроены — проверять нечего). `IMetadataReader` (Icecast/HLS-ридеры) получил `HasMetadata`, `ChannelEngine` — вычисление `MetadataOk` с опросом раз в 500 мс, `EngineStatus.MetadataOk` (`bool?`) прокинут в UI.
- **Ускорен старт прослушивания HLS-потоков.** Причина заметной паузы перед стартом (в отличие от Icecast, который начинает воспроизведение сразу): без `-live_start_index -1` HLS-демуксер ffmpeg по умолчанию начинает с самого старого сегмента, ещё остающегося в окне живого плейлиста, а не с текущего живого края — из-за этого приходится «догонять» через всё уже буферизованное, прежде чем пойдёт актуальный звук. Добавлены `-live_start_index -1` (только для HLS) и `-fflags nobuffer` (для обоих типов потоков) в `StreamCapture.BuildFfmpegArgs`. 2 новых теста.
- **Кнопка ▶/⏹ прослушивания теперь доступна и для остановленных каналов** (раньше требовала идущей записи). При нажатии на неактивный канал `AudioPlaybackService` временно запускает его конвейер захвата только для прослушивания и останавливает обратно при остановке воспроизведения — если канал уже писался по-настоящему, запись не прерывается. Также добавлена подчистка состояния, если исходный канал останавливается сам по себе во время прослушивания (раньше кнопка могла «зависнуть» в состоянии «играет»).
- Зазор между шкалами TP L и TP R на панели индикаторов увеличен с 3 до 5 px.

## 0.00.018 — захват реального stderr ffmpeg при падении сетевого потока

- Расследовали жалобу на постоянные падения `ffmpeg` для канала «Авторадио» (HLS) — не удалось воспроизвести сбой напрямую (стрим сейчас воспроизводится нормально, только одно неопасное предупреждение `Packet corrupt`); похоже на временную проблему на стороне источника потока ~2 часа назад, а не на баг в коде. Добавили тот же буфер (до 16 КБ) и вывод его содержимого в `LogWarning` вместе с кодом возврата при ненулевом коде выхода — при следующем падении в логе будет видна настоящая причина, а не только код.

## 0.00.017 — переход захвата со звуковой карты с BASS на NAudio

- **`SoundcardCapture` полностью переписан с BASS (`ManagedBass`) на [NAudio](https://github.com/naudio/NAudio) (MIT)** — снимает лицензионный вопрос BASS (свободно только для некоммерческого использования) полностью и без оговорок: NAudio бесплатна для любого использования, включая коммерческое.
- Заодно устранён целый класс багов, а не очередной точечный патч: три предыдущих раунда фиксов ложных разрывов соединения со звуковой картой (различение `Stopped`/`Stalled`, повторная проверка через 300 мс, диагностика видимости устройства при коде ошибки `Handle`) были реактивными обходами вокруг того, что BASS не давал ничего, кроме опроса `ChannelIsActive` каждые 500 мс. NAudio's `WasapiCapture` — событийная модель: `RecordingStopped` стреляет ровно при реальном завершении потока с точной причиной в `Exception`, `DataAvailable` — при поступлении данных. Опрос и все таймеры-дебаунсеры убраны за ненадобностью.
- Список устройств (`EnumerateDevices()`) теперь строится через `MMDeviceEnumerator.EnumerateAudioEndPoints(DataFlow.Capture, ...)` — loopback/render-устройства структурно не попадают в эту категорию Windows Core Audio API, поэтому реактивный фильтр `IsLoopback` (введённый в 0.00.014) не портируется, а просто удаляется — фильтровать больше нечего. Проверено на этой машине: список входов идентичен тому, что выдавал BASS (те же 6 реальных устройств), а формат UID (`{0.0.1.00000000}.{guid}`) совпадает с прежним 1-в-1 — уже сохранённые в конфигах `device_uid` продолжают резолвиться без изменений.
- `bass.dll` и пакет `ManagedBass` удалены полностью: из `Quince.Service.csproj`, из `Quince.Service/native/` (папка удалена), плюс убраны бесхозные копии `bass.dll`/`bassmix.dll` в корне репозитория, оставшиеся от более раннего удаления `ManagedBass.Mix`.
- `BassNativeLibraryTests.cs` удалён (проверять больше нечего — NAudio не грузит отдельную нативную библиотеку). `SoundcardCaptureTests.cs` (14 тестов на `ResolveDeviceIndex`) не потребовал изменений логики — только механическое переименование поля `Driver`→`Id`.
- README: убран раздел про лицензию BASS и таблица «Сторонние бинарные компоненты» сокращена до `ffmpeg.exe`/`ffprobe.exe` (у NAudio нет отдельного нативного файла для документирования).
- **Важно**: у нас нет реального проблемного виртуального аудиокабеля (VB-Audio Virtual Cable/Breakaway Pipeline) в этой среде для сквозной проверки — устранение самого КЛАССА ложных разрывов подтверждено на уровне архитектуры (нет больше опроса и гадания по коду ошибки), но реальную стабильность на длительной записи может подтвердить только пользователь на своей машине.

## 0.00.016 — диагностика повторного разрыва soundcard-подключения (код ошибки Handle)

- На новом сообщении о ложном разрыве звуковой карты (`Line 1 (Virtual Audio Cable)`, код ошибки BASS `Handle` вместо ранее виденных `Stopped`/`Stalled`) выяснилось: этот класс ошибки означает, что дескриптор записи стал НАСТОЯЩИМ невалидным (не временная пауза) — предыдущие исправления (различение `Stopped`/`Stalled`, повторная проверка через 300 мс) тут принципиально не помогают, т.к. дескриптор уже мёртв в любом случае, и переподключение — единственный доступный вариант восстановления. По логу видно, что переподключение действительно срабатывает («Переподключение к аудиоустройству выполнено»), просто повторяется часто — похоже на особенность драйвера конкретного виртуального аудиокабеля (сбрасывает pin захвата при простое/переконфигурации), а не на баг в коде.
- Добавлена диагностика: в предупреждение о разрыве добавлено, видно ли устройство в системе прямо в этот момент (`SoundcardCapture.EnumerateDevices()` вызывается заново) — это разграничит на будущее «устройство реально пропало» и «дескриптор умер, а устройство никуда не делось», если проблема повторится снова.

## 0.00.015 — исправлен формат «как во входном потоке», индикаторы метаданных/тишины, устойчивость обнаружения HLS-метаданных

- **Исправлен режим вывода «Как во входном потоке» (`output_format.mode: original`)**: раньше он ничего не делал, кроме отключения ручного пересэмплирования — файл всё равно сохранялся в том `file_format`, что был задан (по умолчанию `mp3`), поэтому HLS/AAC-канал реально писался в MP3. Теперь для этого режима кодек/расширение выбираются автоматически по источнику: `soundcard` → WAV PCM (частота/каналы и так уже брались из входного захвата, не менялись), `hls` → AAC, `icecast`/`icecast_mp3` → MP3. Диалог редактирования канала показывает подсказку «Будет сохранено как: …» под выбором режима; строка «Файл:» на карточке канала тоже теперь показывает реальный итоговый формат, а не сохранённое в конфиге значение.
- **Кнопка «Определить» (метаданные) больше не затирает уже заполненное поле пустым результатом** — раньше неудачная/не успевшая проверка (таймаут, временная сетевая ошибка) молча стирала рабочий URL, который пользователь мог ввести вручную; теперь поле меняется только при успешном обнаружении, а при неудаче показывается причина (если она известна).
- **Обнаружение JSON-эндпоинта метаданных HLS теперь устойчиво к одиночному сетевому сбою**: раньше единственная неудачная попытка при старте канала (например, кратковременная проблема с сетью в момент одновременного старта нескольких каналов) навсегда переводила канал на резервный разбор ID3 через ffprobe на всю сессию, даже если сам JSON-эндпоинт был рабочим. Теперь до 3 попыток обнаружения с паузой 3 с перед резервным вариантом.
- На карточке канала добавлены два новых индикатора в строке заголовка: круглый индикатор метаданных (голубой — режим метаданных настроен, серый — нет; для источников типа «Поток») и живой индикатор наличия сигнала (зелёный — звук есть, красный — тишина, по мгновенному True Peak) — не зависит от отдельно настраиваемого детектора тишины канала (который по умолчанию выключен), поэтому работает всегда. У всех индикаторов и элементов главной страницы (фильтр, пункты бургер-меню, строки карточки канала) добавлены всплывающие подсказки.
- Проверен фильтр списка звуковых устройств (`SoundcardCapture.EnumerateDevices`, введён в 0.00.014) — на тестовой машине корректно исключает loopback-устройства, оставляя только настоящие входы; отдельно отмечено, что некоторые виртуальные аудиокабели (например VB-Audio Virtual Cable) называют свой вход словом «Output» в имени устройства («CABLE Output») — это не баг фильтра, такова схема именования самой программы виртуального кабеля.
- Положение статусной строки на главной странице (под полем фильтра, над списком каналов) проверено — уже соответствует нужному расположению, изменений не потребовалось.

- Добавлен гониометр (стереофазовый осциллограф) — квадратная область фиксированного размера внизу панели индикаторов, отрисовывается на `<canvas>` через небольшой JS-модуль (`wwwroot/goniometer.js`) по децимированным сырым сэмплам L/R, которые теперь передаются с движка записи через новое событие `AudioEngineManager.GoniometerUpdated` (~10 раз/сек, не более ~256 точек за раз).
- Диалог редактирования/создания канала перед сохранением теперь реально проверяет доступность папки записи (`Directory.CreateDirectory` с таймаутом 5 с) — если сетевой путь или диск недоступны, показывается сообщение об ошибке вместо сохранения нерабочего конфига.
- Сохранение канала обёрнуто в try/catch: если конфиг успел исчезнуть (например, удалён из другой вкладки, пока диалог был открыт), пользователь увидит сообщение об ошибке вместо необработанного исключения, которое могло уронить весь Blazor-circuit (и выглядеть как «диалог сам закрылся из-за обновления страницы»).
- **Исправлен независимо найденный критический баг для self-contained сборки (0.00.005)**: `WebApplication.CreateBuilder(args)` по умолчанию берёт корень контента (и, соответственно, `wwwroot`) от рабочей директории ПРОЦЕССА, а не от папки, где лежит сам `.exe` — `ConfigDir`/`LogDir` уже были защищены от этого через `AppContext.BaseDirectory` (`PathResolver`), а встроенный `wwwroot` — нет. Из-за этого при запуске не из папки проекта (в частности — как служба Windows, где рабочая директория по умолчанию `System32`) все статические файлы (`app.css`, `icon.svg`, шрифты, теперь и `goniometer.js`) отдавались бы с 404, и интерфейс выглядел бы полностью без стилей. Раньше это маскировалось тем, что тестирование всегда шло через `dotnet run` из папки проекта. Исправлено явным заданием `ContentRootPath = AppContext.BaseDirectory` в `Program.cs`. Проверено прямым запуском опубликованного `Quince.Service.exe` из посторонней рабочей директории — все статические файлы и главная страница отдаются корректно.

**Незакрытый вопрос**: пользователь также сообщил, что диалог настроек канала иногда самопроизвольно закрывается уже во время работы с ним — конкретную причину подтвердить не удалось (нет браузерного инструмента для интерактивной отладки в этом окружении). Добавленная защита try/catch устраняет один вероятный сценарий (гонка с удалением канала), но не обязательно единственный — см. диалог с пользователем в этой сессии.

## 0.00.005 — самодостаточная (self-contained) публикация

- `Quince.Service.csproj`: добавлены `RuntimeIdentifier=win-x64` и `SelfContained=true`. `dotnet publish` теперь кладёт в выходную папку весь нужный .NET-рантайм — пользователю целевой машины больше не нужно отдельно ставить ASP.NET Core Runtime. Плата за это — размер публикации вырос примерно до 200 МБ.
- Проверено прямым запуском опубликованного `Quince.Service.exe` с `DOTNET_ROOT`, указывающим в никуда (эмуляция машины без установленного .NET) — приложение стартует и отвечает на HTTP без ошибок разрешения рантайма.
- **Важное ограничение, не устранённое этим изменением**: собственно .NET-рантайм теперь встроен, но нативная библиотека `bass.dll` (и `bassmix.dll`) для пакета `ManagedBass`, используемого в `SoundcardCapture`, по-прежнему не бандлится — NuGet-пакет `ManagedBass`/`ManagedBass.Mix` содержит только managed-обёртку. На машине без предустановленного BASS каналы `source.type: soundcard` упадут с `DllNotFoundException` при старте записи. `ffmpeg.exe` (используется `stream`-каналами) уже бандлится в `tools/` и этой проблемы не имеет.

## 0.00.004 — редактирование/клонирование/удаление канала, меню, индикаторы, вход со звуковой карты

- Реализована полная мутация каналов: создание, редактирование, клонирование, удаление (`ChannelManager.Add/Update/Delete/Clone`), с YAML-файлами конфигов в `config/` через уже существовавший `YamlConfigLoader.Save()`. `AudioEngineManager` реагирует на изменения «на лету» — перезапускает движок при правках, переносит его на новый ключ при переименовании канала, останавливает при удалении.
- UI: кнопки ✎/⧉/✕ на карточке канала теперь рабочие (модальный диалог редактирования/создания, подтверждение удаления, мгновенное клонирование).
- Окно индикаторов (▦) реализовано как модальная панель — True Peak L/R и LUFS (M/S/I) по одному каналу или сразу по всем.
- Бургер-меню полностью довязано: новый канал, настройки приложения, обновить конфигурацию (пересканирование `config/`), перезапуск/выход приложения, старт/стоп записи всех каналов, индикаторы, показать README.md.
- Настройки приложения (`app.yaml`) редактируются через UI и применяются вживую без перезапуска: уровень логирования и срок хранения логов (новый `AppSettingsService` + `FileLoggerProvider.UpdateSettings`), а также пороги/цвета индикатора уровня (используются теперь и в карточке канала, и в окне индикаторов вместо старого статичного градиента).
- Реализован вход со звуковой карты (`source.type: soundcard`): новый `SoundcardCapture` на `ManagedBass` (пакет был в зависимостях с версии 0.00.001, не использовался) с выбором устройства по `device_uid`/`device_name`/`device_index` и реконнектом по той же схеме статусов, что и у потокового источника. `StreamCapture`/`SoundcardCapture` теперь реализуют общий интерфейс `IAudioCapture`, `ChannelEngine` выбирает нужный по `source.type`. Кнопка Старт/Стоп для таких каналов больше не задизейблена.
- README.md теперь копируется рядом со скомпилированным приложением и доступен из меню «Показать файл README.md».

**Известные ограничения**: вход со звуковой карты не проверялся на реальном оборудовании (только модульные тесты логики выбора устройства); метаданные потока (ICY/HLS — название трека) всё ещё не реализованы; папка `config/RP/` (~150 доп. станций) по-прежнему не читается рекурсивно.

## 0.00.003 — защита обработчиков событий в AudioEngineManager

- Исправлена критическая уязвимость: `PushLevel` и `PushStatus` теперь оборачивают вызовы событий в try/catch с логированием. Конкретный риск: если обработчик события в `ChannelCard` выбросит исключение (например, `InvokeAsync` на разорванном Blazor-circuit), исключение распространялось бы из `ChannelEngine.MonitorAsync` или `SilenceDetector.RunAsync`, молча убивая background-task этого канала навсегда без логирования. Теперь все исключения отловлены и залогированы.

## 0.00.002 — аудио-движок для stream-каналов

- Реализован полный конвейер записи для каналов `source.type: stream` (Icecast/HLS): `StreamCapture` (ffmpeg-подпроцесс, декодирование, реконнект), `AudioWriter` (ротация по временной сетке, retention), `LevelMeter` (True Peak + LUFS, EBU R128), `SilenceDetector`.
