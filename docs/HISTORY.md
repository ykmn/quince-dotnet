> Продолжай адаптацию аудио-движка

(Далее пользователь короткими репликами подтверждал каждый этап: «да, продолжай» — после раздела архитектуры дизайн-документа; «да, продолжай» — после раздела компонентов; «да» — после раздела оркестрации/UI; «желаемый дизайн будем доделывать отдельно?» — уточнение процесса, подтверждено; «Продолжай разработку» — переход к написанию плана реализации; «1» — выбор Subagent-Driven Development из двух предложенных вариантов выполнения; «Продолжим» — после того как один из сабагентов был прерван лимитом сессии посередине Задачи 11.)

**Ответ:** Спланировал и реализовал первый полноценный срез аудио-движка — целиком для каналов `source.type: stream` (Icecast/HLS), поскольку это покрывает подавляющее большинство реальных конфигов. Прочитал легаси Python-реализацию (`../quince/src/audio/*.py`) как референс для порта.

Через `superpowers:brainstorming` собрал дизайн (уточнил у пользователя: полный пайплайн для одного типа источника вместо разбивки по подсистемам; stream раньше soundcard; декодирование через ffmpeg-подпроцесс как в легаси, а не через ManagedBass; бинарники ffmpeg — получить официальную сборку и забандлить). Сохранил спецификацию в `docs/superpowers/specs/2026-07-05-audio-engine-stream-pipeline-design.md`.

Через `superpowers:writing-plans` составил план из 15 задач (`docs/superpowers/plans/2026-07-05-audio-engine-stream-pipeline.md`) и выполнил его через `superpowers:subagent-driven-development` — отдельный свежий сабагент-реализатор и отдельный сабагент-ревьюер на каждую задачу, с циклами доработки при найденных проблемах.

Реализовано: `AudioChunk`, `OutputPathPlanner` (даты/ротация), `KWeightingFilter`/`TruePeakCalculator`/`LufsCalculator` (EBU R128: True Peak + LUFS), `LevelMeter`, `SilenceDetector` (RMS-гистерезис), `StreamCapture` (ffmpeg-подпроцесс, реконнект), `AudioWriter` (ротация файлов по временной сетке, retention), `ChannelEngine` (оркестрация), `AudioEngineManager` (`IHostedService`, авто-старт, управление по каналам). Добавлен проект `Quince.Service.Tests` (xUnit) с юнит-тестами для всей чисто логической части. Забандлен `ffmpeg.exe` (официальная сборка gyan.dev) в `Quince.Service/tools/`. UI: кнопка Старт/Стоп в `ChannelCard.razor` теперь реально управляет записью через `AudioEngineManager`, статус-точки и индикатор уровня получают живые данные через SignalR (`LevelHub`), с корректной инициализацией состояния при подключении нового клиента.

По ходу ревью были найдены и исправлены реальные ошибки в собственном плане (не в реализации): `OpenProc` не применял cooldown при сбое запуска ffmpeg (только при сбое записи) — исправлено; `ChannelEngine._status` изменялся из трёх потоков без синхронизации — добавлена блокировка; в `ChannelCard.razor` не хватало пакета `Microsoft.AspNetCore.SignalR.Client` (упущение в плане) — добавлено; коллбэки SignalR могли вызвать `InvokeAsync` на уже освобождённом компоненте — добавлена проверка `_disposed`.

Сквозная ручная проверка (без браузера — только через `auto_start`, вручную браузерный UI не проверялся) подтвердила: реальная запись с живой радиостанции («Радио Маяк»), растущий mp3-файл, корректный формат строк лога, чистая остановка без осиротевших процессов ffmpeg.

Репозиторий не под git; при попытке инициализировать его для процесса ревью выяснилось, что `M:\` — сетевой SMB-диск (Mac), не позволяющий git писать объекты (падает при переименовании read-only файлов) — по решению пользователя выполнение продолжено без git, с ревью по фактическим файлам вместо диффов.

**Известные ограничения после этой доработки**: захват со звуковой карты (`source.type: soundcard`) и метаданные потока (ICY/HLS) по-прежнему не реализованы; окно индикаторов (▦) и редактирование/клонирование/удаление канала остаются визуальными заглушками; `config/RP/` (~150 доп. станций) по-прежнему не сканируется рекурсивно (решение принято ранее, подтверждено при тестировании).

После завершения плана из 15 задач и упомянутого выше критического пост-планового исправления сериализации SignalR/JSON, финальное ревью всей ветки выявило проблему масштабируемости: каждая `ChannelCard` открывала собственное SignalR-подключение обратно к тому же серверу (`/hubs/level`) — при реальной нагрузке в 166 каналов это означало бы десятки-сотни избыточных loopback WebSocket-соединений внутри одного Blazor-circuit. Владелец проекта принял решение полностью убрать `LevelHub`/SignalR из приложения и заменить его прямыми in-process C#-событиями `AudioEngineManager` (`LevelUpdated`/`StatusUpdated`), на которые каждая `ChannelCard` подписывается напрямую, полагаясь на собственный circuit Blazor Server для доставки обновлений в браузер. Побочным эффектом стало и устранение самого класса бага, который чинило то самое исправление сериализации: события передают живые ссылки на объекты без границы сериализации, так что проблема с `double.NegativeInfinity` в JSON больше не может возникнуть в принципе.

Архитектурная замена в-процесс событий завершена, но во время независимого ревью выявлена критическая уязвимость: `PushLevel` и `PushStatus` в `AudioEngineManager` вызывали события без защиты — если обработчик события выбросит исключение (например, `InvokeAsync` на разорванном Blazor-circuit), исключение пройдёт через `ChannelEngine.MonitorAsync` или `SilenceDetector.RunAsync`, которые ловят только `OperationCanceledException`, молча убивая background-task этого канала навсегда без логирования. Исправлено обёртыванием обоих вызовов событий в try/catch с `_logger.LogError` — идентично защите, уже имевшейся в `LevelMeter.ProcessChunk`. Версия обновлена до 0.00.003, CHANGELOG.md и HISTORY.md актуализированы, сборка переопубликована.

Новая логика (`ChannelCard.MetadataHealthDotClass`): серый, если запись не идёт; красный — только если для канала настроена ссылка на метаданные, но они не определяются после 30-секундного периода ожидания (покрывает худший случай HLS-обнаружения — несколько попыток JSON-эндпоинта плюс ID3-пробник); зелёный иначе, включая каналы без метаданных вовсе. `IMetadataReader` (оба ридера — Icecast и HLS — уже имели приватное поле `HasMetadata`) получил его в интерфейс; `ChannelEngine` считает `MetadataOk` (`bool?`) с той же периодичностью 500 мс, что и раньше отслеживался `ReconnectAttempt`, и прокидывает через `EngineStatus.MetadataOk`. ## 51

**Запрос:**
> У HLS-каналов Carlo индикаторы иногда застывают, для Icecast в это время продолжают двигаться. Давай сделаем диагностику

**Ответ:** Диагностика: индикаторы уровня (`LevelMeter`) обновляются только когда в `StreamCapture.ReadLoopAsync` приходят новые байты от ffmpeg через `stream.ReadAsync(...)` — этот `await` не имел таймаута. Если ffmpeg зависал (не выходил, не писал в stderr, просто переставал отдавать байты в stdout), цикл чтения ждал бы вечно: без ошибки, без выхода процесса, без срабатывания reconnect-логики (`_reconnectAttempt` оставался 0, `_status` — `Streaming`) — индикаторы молча замирали на последнем значении. Специфично для HLS больше, чем для Icecast: Icecast — один непрерывный TCP-поток, где сбой почти всегда рвёт соединение (получаем `n == 0`/exception → reconnect срабатывает штатно); HLS — ffmpeg сам опрашивает live-плейлист и подтягивает сегменты, и застревание на этом (сервер не отдаёт очередной сегмент/плейлист не продвигается) — известный класс зависаний HLS-демуксера ffmpeg, не проявляющийся ни выходом процесса, ни stderr.

Предложил пользователю добавить watchdog по таймауту простоя чтения; уточнил область (только HLS vs все типы потоков) — выбрано "для всех типов потоков". Реализовано в `StreamCapture.cs`:
- `StallTimeout = 30s` — если `ReadLoopAsync` не получает от ffmpeg ни байта дольше этого времени, чтение прерывается через `CancellationTokenSource.CreateLinkedTokenSource(ct)` + `CancelAfter(StallTimeout)`, перезапускаемый (`CancelAfter` вызывается заново) при каждой попытке чтения — то есть таймер сбрасывается любым прогрессом, а не только полным заполнением буфера.
- Добавлено приватное исключение `StreamStallException`, которое `RunLoopAsync` ловит отдельным `catch` (специфичное предупреждение "Зависание ffmpeg: ... — перезапуск") перед общим `catch (Exception ex) when (ex is not OperationCanceledException)` — дальше срабатывает уже существующая логика реконнекта (kill процесса в `finally`, инкремент `_reconnectAttempt`, задержка, повтор), никакой новой ветки поведения придумывать не пришлось.
- Настоящая отмена по `ct` (штатная остановка канала) по-прежнему распознаётся отдельно (`when (!ct.IsCancellationRequested)`) и не превращается в `StreamStallException` — `OperationCanceledException` от реальной остановки продолжает вести себя как раньше.

Проверено: `dotnet build` для `Quince.Service` и `Quince.Service.Tests` — 0 ошибок в обоих; юнит-тестов, напрямую дёргающих приватные `ReadLoopAsync`/`RunLoopAsync`, нет (grep подтвердил), так что новая логика не затронула существующие тесты.
```csharp
audioSeconds += chunk.FrameCount / (double)_sampleRate;
var ahead = audioSeconds - (DateTime.UtcNow - realStart).TotalSeconds;
if (ahead > 0.2)
    await Task.Delay(TimeSpan.FromSeconds(ahead - 0.1), ct);
```

Это темп-регулятор: если обработка чанков обогнала реальное время (например, после паузы в подаче данных консьюмер быстро разбирает накопившийся в bounded-канале бэклог — `await foreach` отдаёт буферизованные чанки почти без задержки между ними), код намеренно засыпает через `Task.Delay`, чтобы "досинхронизироваться" с реальным временем. Проблема: пока идёт эта компенсирующая пауза, `_onUpdate`/`InvokeAsync` вообще не вызываются — то есть любая исходная пауза в поступлении чанков (сбой захвата, backpressure bounded-канала, конкуренция за поток) эффективно УДВАИВАЕТСЯ по видимой длительности фриза: сначала тишина из-за самой паузы, потом ещё одна тишина такой же длины из-за компенсирующего сна — и оба происходят целиком внутри `LevelMeter.RunAsync`, ДО того как хоть один `InvokeAsync` будет запрошен, поэтому диагностика 0.00.043 (которая начинает мерить время только с момента вызова `InvokeAsync`) этот механизм в принципе не могла увидеть.

Добавил два целевых замера прямо в `RunAsync` (тот же порог 300мс, что и в UI-диагностике 0.00.043, для единообразия):

- **"Пауза синхронизации темпа LevelMeter"** — длительность самого компенсирующего `Task.Delay`, если он превышает порог — прямое подтверждение/опровержение гипотезы про удвоение фриза.

Поведение темп-регулятора не менял — это осознанный дизайн (не показывать "перемотанные вперёд" уровни после паузы), трогать его без подтверждения гипотезы логами не стал.

Как только реальные данные возобновляются, `ProcessChunk` просто перезаписывает `_lastReading`/`_lastRealUpdateAt` под тем же локом (`_readingLock`, общий между `ProcessChunk` и `DecayTick` — оба могут исполняться на разных потоках одновременно) — новое реальное значение естественным образом перекрывает затухающее, никакой явной синхронизации между режимами не требуется.

Это **чисто косметическое сглаживание** — саму паузу в поступлении данных не устраняет и не может устранить (см. записи #54-58), только меняет то, как она выглядит на экране: вместо мёртвой неподвижности индикатор плавно оседает к тишине и обратно взлетает при возобновлении данных, как и ведёт себя настоящий физический измеритель уровня при кратковременной потере сигнала.

Для тестируемости `DecayTick`/`Decay`/`DecayValue`/`IsFullyDecayed` сделаны `internal` (как уже было с `ProcessChunk`) — добавил 6 новых тестов в `LevelMeterTests.cs`: не срабатывает сразу после реального обновления (внутри grace window), срабатывает и даёт значение ниже последнего реального после ожидания (единственный тест с реальным `await Task.Delay(300)`, остальные детерминированные), плюс прямые проверки чистой математики `DecayValue`/`IsFullyDecayed` (шаг затухания, сохранение `-∞`, схлопывание за порогом).

Живой визуальный эффект (плавное "оседание" индикатора вместо замирания) можно подтвердить только на реальном UI пользователя. Версия обновлена до 0.00.048.

- **Новый `Audio/PlayoutBuffer.cs`** — буферизует `TargetDelaySeconds` (по умолчанию 12с, запас над худшим замером — Радиус FM Минск ~10с) аудио перед отдачей ("прайминг" — пока запас не набран, потребитель не получает вообще ничего, и уже существующий децей-таймер `LevelMeter` сам корректно покажет спад к тишине без всякого специального кода для этого случая). - Обёрнуты `PlayoutBuffer`'ом только два потребителя, которые смотрит/слушает человек: `"meter"`-подписка в `Audio/ChannelEngine.cs` (перед созданием `LevelMeter`) и `"browser-playback-{guid}"`-подписка в `Services/AudioStreamEndpoint.cs` (перед кодированием в MP3 для прослушки) — с одной и той же задержкой, так что звук и индикатор остаются синхронны друг с другом.

Обоснование: архиву задержка перед записью не даёт пользы, зато добавляет риск потери ~12с аудио в памяти при аварийном завершении процесса и не должна сдвигать ротацию файлов по временной сетке; детектору тишины важна оперативность оповещения о реальной проблеме, а не сглаженная картинка.
- `Audio/LevelMeter.cs`: убран раздел вычисления/логирования "сырой" паузы в `RunAsync` — теперь `LevelMeter` в норме получает чанки уже через `PlayoutBuffer`, и пауза на ЕГО собственном reader'е означала бы просто "буфер ещё не наполнился/иссяк", а не "источник встал", так что старое логирование там стало бы вводящим в заблуждение (ложная тревога на каждый старт канала, пока буфер набирает 12с). Само диагностическое логирование этой паузы перенесено в `PlayoutBuffer` (там, где сырая пауза источника ещё видна как есть), порог поднят с 300мс до 1000мс, чтобы не забивать лог мелким безобидным джиттером вроде Love Radio.

Проверено: `dotnet build` для `Quince.Service` и `Quince.Service.Tests` — 0 ошибок/предупреждений в обоих. `dotnet test` по-прежнему недоступен на этой машине (несовпадение версии рантайма 8.0.28/8.0.27, см. записи 31-33/46) — как и в записи 46, написал отдельный самодостаточный self-contained консольный harness (`ProjectReference` на `Quince.Service.csproj`) вне репозитория, который гоняет реальный `PlayoutBuffer` (настоящие `Start()`/`Stop()`, настоящие фоновые задачи, не только синхронные вызовы `Enqueue`/`ReleaseDue` из юнит-тестов) против симулированного источника, максимально близко воспроизводящего реальный лог: ~6.0с содержимого, доставленного почти мгновенно ("пачкой", как в реальности целый HLS-сегмент), затем пауза, полный период ~6.05с (контента чуть меньше периода — реалистично, источник не может вечно опережать реальное время). ## 64

**Запрос:**
> У канала который записывается старт воспроизведения начинается с большой паузы, индикаторы не совпадают со звуком давай уточним.

Затем, после уточняющих вопросов (пауза оказалась "заметно больше 15с (20-30с+)", и звук "продолжает заметно отставать от индикатора" даже после старта — не только долгий старт, а постоянный дрейф), и ещё одно сообщение в той же сессии:
> При нажатии воспроизведения на канале запись которого остановлена кнопка "Старт записи" переключается в нажато ("Стоп записи"), так не должно быть

**Ответ:** Заход через `/plan`. Разведка кода (`Audio/PlayoutBuffer.cs`, написанный в предыдущей сессии) нашла конкретную причину дрейфа: внутренний канал-хэндофф потребителю (`_output`) был **неограниченным** (`Channel.CreateUnbounded`). `ReleaseDue()` пишет в него по расписанию реального времени независимо от того, успевает ли потребитель вычитывать — если потребитель (метр или, что куда вероятнее, длинная цепочка `AudioStreamEndpoint`: запись в stdin ffmpeg → MP3-кодирование → запись в HTTP-ответ → собственная буферизация браузера перед стартом `<audio>`) хоть раз ненадолго отстал, в неограниченном канале накапливается очередь устаревших чанков, которая **никогда не обрезается** — потребитель просто доигрывает всё по порядку, когда успевает, то есть один временный затык превращается в постоянный, только растущий сдвиг. Это объясняло оба симптома разом: у пути прослушки объективно намного больше мест, где может на секунды притормозить, чем у пути метра (простой C#-делегат → SignalR), отсюда и лишний хвост именно у звука; а раз хвост не обрезается — отставание не проходит и после старта воспроизведения. Этот сценарий (медленный потребитель) не был покрыт тестами/harness'ем в прошлой сессии, поэтому не был замечен раньше.

По второй жалобе — разведка подтвердила: `EngineStatus` имел только один флаг `IsRecording`, означавший на деле "движок канала вообще запущен" (`ChannelEngine.Start()` шлёт его безусловно, независимо от того, был ли создан `AudioWriter`). `ChannelCard.razor` рисует кнопку Старт/Стоп ЗАПИСИ по этому же флагу. `AudioPlaybackService.Play()` — если канал не запущен, сам временно автозапускает конвейер захвата ("just for the duration of playback" — по собственному комментарию в коде), что не только ложно переключало кнопку, но и по факту **начинало настоящую запись в файл**, если у канала `RecordAudio: true` (обычная настройка) — расходясь с собственным заявленным намерением кода.

Реализовано:
- **`Audio/PlayoutBuffer.cs`**: `_output` заменён с `Channel.CreateUnbounded` на **ограниченный** канал (`Channel.CreateBounded`, ёмкость 30 чанков ≈ несколько секунд, `FullMode = BoundedChannelFullMode.DropOldest`). Если потребитель отстал — при переполнении отбрасываются САМЫЕ СТАРЫЕ ещё не отданные чанки в пользу свежих, поток самокорректируется обратно к целевому ~12с отставанию вместо необратимого дрейфа. Одно изменение чинит и метр, и прослушку сразу (общий класс).
- **`Audio/EngineStatus.cs`**: новое поле `IsFileRecording` (true только когда реально создан `AudioWriter`), отдельно от `IsRecording` (движок запущен по любой причине, в т.ч. временно ради прослушки) — намеренно НЕ переиспользовал `IsRecording` для этого, чтобы не сломать уже работающую фичу живого индикатора при прослушке остановленного канала (она как раз держится на `IsRecording`).
- **`Audio/ChannelEngine.cs`**: `Start()` получил `bool suppressRecording = false` — при `true` пропускает создание `AudioWriter`, даже если `RecordAudio: true`; `EngineStatus` в `Start()` заполняется `IsFileRecording: _writer != null`.
- **`Services/AudioEngineManager.cs`**: `Start(string, bool suppressRecording = false)` прокидывает параметр в `ChannelEngine.Start`.
- **`Services/AudioPlaybackService.cs`**: `Play()` теперь вызывает `_engineManager.Start(channelName, suppressRecording: true)` — устраняет побочную настоящую запись.
- **`Pages/Shared/ChannelCard.razor`**: кнопка Старт/Стоп ЗАПИСИ переключена на `_status.IsFileRecording`. Всё остальное, что было завязано на `IsRecording` (цвет рамки/точки статуса, точка "звук", сброс уровня при остановке), сознательно не тронуто. `ToggleRecording()` доработан на случай "канал уже запущен только ради прослушки, а пользователь нажал Старт записи" — раз `AudioEngineManager.Start()` не делает ничего для уже запущенного канала, в этом случае сначала `Stop()`, потом `Start()` заново без подавления записи (кратко прерывает текущую прослушку — принятый компромисс для редкого одновременного случая).
- Новый регрессионный тест `PlayoutBufferTests.ReleaseDue_ConsumerFallsBehind_DropsOldestKeepsNewestWithinCapacity` — 50 маркированных чанков без чтения потребителем, проверка что после переполнения остаются только последние ≤30 по порядку.

Проверено: `dotnet build` для `Quince.Service` и `Quince.Service.Tests` — 0 ошибок/предупреждений в обоих. `dotnet test` по-прежнему недоступен (см. записи 31-33/46/61/63) — как и раньше, написан отдельный self-contained консольный harness вне репозитория (тот же приём, что и в записи #61, только с `<AssemblyName>Quince.Service.Tests</AssemblyName>`, чтобы получить доступ к `internal`-членам через `InternalsVisibleTo`), который прогнал именно новый drop-oldest тест против реального `PlayoutBuffer` — подтверждено: из 50 отправленных чанков остались ровно последние 30, по порядку, самые старые (0-19) отброшены. Живое измерение реальной задержки/дрейфа звука в этой среде недоступно (нужен реальный HLS-поток и браузер, слушающий больше пары минут) — итоговое полевое подтверждение, как и вся эта сага, за пользователем. Версия обновлена до 0.00.053.

**Ответ:**

## 83

**Запрос:**
> (скриншот — вкладка Recovery в свойствах службы «Quince Audiologger», все три «failure» на «Restart the Service») Функция рестарта сервиса через GUI не работает: в логе "Айва останавливается", и ничего не происходит. Настройки сервиса Windows:

**Ответ:** Диагностировано (без изменения кода на этом шаге): `DoRestart()` вызывает `IHostApplicationLifetime.StopApplication()` — штатную, «чистую» остановку, о которой `WindowsServiceLifetime` отчитывается перед SCM как `SERVICE_STOPPED` без ошибки. **Запрос:**
> У канала превышен предел попыток переподключения. Нужно чтобы по ручному нажатию на Старт он снова в цикле пытался соединиться, вдруг соединение снова доступно.

**Ответ:** Найден реальный баг в `Services/AudioEngineManager.cs`. `OnReconnectExhausted` (в `ChannelEngine`) останавливает канал напрямую, минуя `AudioEngineManager.Stop()` — поэтому запись о нём оставалась в `_engines`, а `Start()` при виде уже существующего ключа просто выходил (`if (_engines.ContainsKey(...)) return;`), не запуская новый цикл подключения. Клик «Старт» на карточке в состоянии ошибки не делал вообще ничего. Тот же изъян был в `IsRunning()` (голый `ContainsKey`) — из-за него «Запустить запись всех каналов» тоже молча пропускал упавшие по ошибке каналы, и авто-старт для прослушки (`AudioPlaybackService`) не мог поднять такой канал даже по ▶.

Оба метода переведены на проверку `engine.Status.IsRecording` вместо факта присутствия в словаре; `Start()` при обнаружении «мёртвой» (остановившейся по ошибке) записи удаляет её и создаёт канал заново обычным путём. Проверено вживую (Playwright + разбор лог-файла, канал с заведомо недоступным адресом `http://127.0.0.1:1/...`, `reconnect_max_attempts: 1`): канал дошёл до `HasError` («Достигнут предел попыток переподключения»), ручной «Старт» тут же запустил новый цикл («попытка 0» в логе сразу после клика, статус-точка вернулась в «Запись идёт», рамка карточки перестала быть красной).

## 99

**Запрос:**
> Сессия браузера через некоторое время бездействия теряет связь с приложением: в браузере Reconnecting.... и не соединяется до обновления страницы. Как это можно исправить?

**Ответ:** Через режим планирования (`EnterPlanMode`/`ExitPlanMode`) — план утверждён пользователем без правок сути. Причина: `AddServerSideBlazor()` без опций — дефолтные `DisconnectedCircuitRetentionPeriod` (3 мин) и SignalR `ClientTimeoutInterval` (30с) рассчитаны на активную вкладку; фоновая/неактивная вкладка (браузер придерживает JS-таймеры), сон ноутбука, короткий сетевой сбой легко их превышают — сервер выбрасывает circuit, а штатный клиентский реконнект `blazor.server.js` (небольшое фиксированное число попыток) исчерпывается впустую.

Реализовано три слоя: (1) `Program.cs` — `DisconnectedCircuitRetentionPeriod` до 15 минут, `ClientTimeoutInterval`/`KeepAliveInterval` до 60с/15с; (2) `Pages/_Host.cshtml` — `blazor.server.js` на `autostart="false"` + явный `#components-reconnect-modal` + новый `wwwroot/reconnect.js` с ручным `Blazor.start()` и увеличенным окном повторных попыток (30×3с ≈ 90с); (3) в том же `reconnect.js` — `MutationObserver` на классы `components-reconnect-failed`/`-rejected`: как только весь ресурс попыток исчерпан или сервер явно отверг старый circuit, страница сама перезагружается вместо мёртвого баннера. `app.css` — минимальное тематическое оформление баннера.

Проверено вживую самодостаточным Playwright-тестом (сам поднимает и убивает процесс `Quince.Service.exe`, без ручной координации): убийство сервера показывает баннер «⚠️ Переподключение к серверу…» за 1с; повторный запуск сервера (новый процесс — старый circuit гарантированно недействителен, воспроизводит именно жалобу пользователя) приводит к автоматической перезагрузке страницы и полному восстановлению интерактивности за 1с после того, как сервер снова стал доступен — без единого ручного действия. Более мягкий сценарий (эмуляция offline через Playwright/CDP) оказался ненадёжен для теста — уже установленный WebSocket не рвётся эмуляцией сразу, поэтому проверка велась через реальное убийство/перезапуск процесса.

Версия обновлена до 0.00.072; `docs/CHANGELOG.md`/`README.md` обновлены, опубликована `Release`-сборка в `release/0.00.072/`.
