# Livewire AoIP — заметки по протоколу (реверс-инжиниринг)

> Собрано в проекте Quince (`quince-dotnet`) по реальному трафику с боевой Axia Livewire-сети
> (Wireshark, `report.pcapng`, множество устройств: xNode-подобные узлы, Rio-подобные бридж-устройства,
> сторонние приложения-логгеры). Ничего из этого не задокументировано публично Telos/Axia — только
> сама multicast-адресация аудио (`239.192.0.0 + N`) подтверждена открытыми источниками
> (docs.telosalliance.com, github.com/kylophone/a-look-at-livewire). Всё остальное ниже — только
> из наблюдения за живыми пакетами, проверено перекрёстно на нескольких независимых полях (см. раздел
> «Как проверялось»). Официально задокументированный способ получить те же данные (точнее, имена
> каналов, которых Advertisement не даёт) — **LWRP** (Livewire Routing Protocol, TCP порт 93,
> текстовый протокол, есть открытые реализации) — раздел 3, проверено на реальном ответе с боевого
> узла, не только по документации реализации.

## 1. Аудио (RTP) — задокументировано публично, для полноты

- Мультикаст-адрес источника (канала) N: `239.192.(N div 256).(N mod 256)`, N в диапазоне 1..65535
  (на практике устройства Axia ограничивают до 32767).
- `239.193.x.x` — тот же номер, но диапазон «To»/backfeed (mix-minus), `239.196.x.x` — surround.
- Аудио — RTP на **UDP-порту 5004**, `L24/48000/2` (24-бит PCM, 48 кГц, стерео) для стандартного
  Livewire; реальный источник иногда физически моно, при этом всё равно объявляется стерео в SDP —
  см. `Quince.Service/Audio/LivewireCapture.cs` и `SourceConfig.LivewireStereo`.

## 2. Advertisement — самореклама узла (реверс-инжиниринг, этот документ)

**Адрес:** `239.192.255.3` (это "верхняя" часть адресного пространства "From"-каналов —
239.192.255.x, реальным аудио-источникам такие номера практически никогда не присваивают, поэтому
адрес свободен под служебный трафик).

**Порт:** не является общеизвестной константой протокола (в отличие от 5004 для аудио) — определяется
захватом трафика на конкретной сети. На сети, где снималось это исследование, был **4001**.
Единственный способ узнать порт на новой сети — Wireshark с фильтром `ip.addr==239.192.255.3` и
посмотреть на `Destination Port` в UDP-заголовке.

**Кто шлёт:** каждое Livewire-совместимое устройство/приложение в сети — включая узлы без единого
источника (`NUMS=0`, чистые слушатели/логгеры) — периодически (наблюдалось раз в несколько секунд)
широковещательно объявляет себя. **Это не протокол запрос/ответ** — не найдено ни одного пакета другой
структуры (разный первый байт `0x03`, разная семантика) за всё время наблюдения; вероятно, отдельного
"запроса" просто нет, только периодический heartbeat.

### 2.1 Структура пакета

```
Смещение   Размер   Содержимое
0          4        Магическое число: 03 00 02 07 (константа во всех наблюдавшихся пакетах —
                     вероятно тип сообщения + версия формата)
4          4        Счётчик/CRC — меняется от пакета к пакету у одного устройства, у повторно
                     захваченного идентичного пакета — совпадает. Не нужен для извлечения каналов.
8          8        Резерв — обычно нули, но у одного устройства в захвате наблюдался неочищенный
                     "мусор" (обрывок текста "led.\nThi..." — вероятно недоинициализированная память
                     на устройстве). Не используется парсером, только пропускается.
16         ...      Последовательность полей (см. 2.2), до конца UDP-полезной нагрузки.
```

### 2.2 Формат поля (TLV)

```
<тег: 4 байта ASCII><тип: 1 байт><значение>
```

Тип определяет размер значения (кроме строк, у которых явная длина):

| Байт типа | Размер значения | Замечено на полях |
|---|---|---|
| `0x00` | 1 байт | `NEST`, `INDI` |
| `0x07` | 1 байт | `ADVT`, `SHAB`, `FAST`, `FASM`, `BAST`, `BASM`, `STPL` |
| `0x06` | 2 байта | `TERM`, теги-источники `S0NN` |
| `0x08` | 2 байта | `PVER`, `HWID`, `UDPC`, `NUMS` |
| `0x01` | 4 байта | `ADVV`, `INIP` (как IPv4), `PSID`/`FSID`/`BSID`/`LPID` (как IPv4 или int32 — см. ниже), `TYPE` (как 4-символьный ASCII-код) |
| `0x09` | 8 байт | `BUSY` |
| `0x03` | переменный | далее 2 байта big-endian длины, потом столько же байт значения, дополненного нулями до этой длины (используется для строк: `ATRN`, `PSNM`) |

Смысл значения зависит от **имени тега**, тип байта задаёт только его размер на проводе (одинаковый
размер `0x01`=4 байта используется и для чистого int32-счётчика, и для IPv4-адреса, и для
4-символьного ASCII-кода — это нормально, не баг парсинга).

Порядок полей в наблюдавшихся пакетах фиксирован, но парсер их не требует — читает как поток
`тег→значение`, что упрощает выживание при добавлении/пропуске необязательных полей в будущих
прошивках.

### 2.3 Поля уровня устройства (один раз в начале пакета)

| Тег | Смысл | Пример значения |
|---|---|---|
| `NEST` | неизвестно (число) | 3, 7, 20 |
| `PVER` | версия протокола Advertisement | 2 (константа во всех образцах) |
| `ADVT` | неизвестно (число) | 1, 2, 3 |
| `TERM` | неизвестно (число) | 13, 45, 84, 93 |
| `INDI` | неизвестно (число) | 1, 5, 6, 7 |
| `ADVV` | неизвестно, опционален | 3, 5, 27 — отсутствует у некоторых устройств |
| `HWID` | младшие 2 байта собственного IPv4 устройства | `172.22.0.49` → `0x0031` |
| `INIP` | собственный IPv4-адрес устройства целиком | `172.22.0.49` |
| `UDPC` | другой служебный UDP-порт (не 4001, не 5004) | `4000` — константа во всех образцах |
| `NUMS` | сколько источников (`S0NN`-блоков) устройство рекламирует дальше; `0` — валидное значение (чистый слушатель) | 0, 1, 2, 4, 15, 16 |
| `TYPE` | код модели/типа устройства, 4 ASCII-символа | `"NX12"` |
| `ATRN` | имя/модель узла, строка | `"EP-xNode-V"`, `"Studio2-Nx12"`, `"logger1"` — опционален |

### 2.4 Блок источника (повторяется `NUMS` раз, может быть 0)

Начинается тегом, буквально равным `"S001"`, `"S002"`, ... `"S016"` — **зеро-паддинг из 3 цифр,
номер позиции источника на устройстве, не сам номер Livewire-канала и не обязательно идёт подряд**
(например, устройство с источниками только в слотах 1 и 3 пришлёт `S001`, затем сразу `S003`).
Значение самого этого тега — не канал, служебное число (наблюдалось 0x65/0x1c — константы, судя по
всему привязанные к варианту прошивки, а не к конкретному источнику).

Дальше, до следующего `S0NN`-тега или конца пакета — поля этого источника:

| Тег | Смысл | Проверено как |
|---|---|---|
| `INDI` | неизвестно | — |
| **`PSID`** | **номер Livewire-канала (то самое N в адресе `239.192.X.Y`)** | int32 |
| `SHAB` | неизвестно | — |
| `FSID` | тот же номер канала, закодированный как IPv4 `239.192.X.Y` | **совпадает с PSID** через `239.192.(N div 256).(N mod 256)` — перекрёстная проверка |
| `FAST`, `FASM` | неизвестно | — |
| `BSID` | номер backfeed/mix-minus для этого источника, как IPv4 `239.193.X.Y` | тот же N, диапазон 239.193.x.x |
| `BAST`, `BASM` | неизвестно | — |
| `LPID` | дублирует `PSID` (тот же int32) | — |
| `STPL` | неизвестно | — |
| **`PSNM`** | **имя канала** (строка) | `"from Codec"`, `"Mic 4 DJ"`, `"Hybrid1"`.."Hybrid4" |
| `BUSY` | занятость источника (0/иное), встречается **вместо** `SHAB..PSNM` у части устройств («облегчённый» вариант блока — есть только `INDI`+`PSID`+`BUSY`, имени нет вообще) | 8-байтовое число, наблюдался только 0 |

**Важно:** `PSNM` есть не у всех устройств/источников. У части устройств (в захвате — узел с 16
источниками) блок источника ограничен `INDI`+`PSID`+`BUSY`, имени нет. Приложение в этом случае
показывает пользователю номер канала и, отдельно, `ATRN` устройства-источника (см. ниже) — **не**
придумывает имя из воздуха.

### 2.5 Конец списка источников

После последнего блока источника (или сразу после `NUMS`, если их 0) — сентинел:
```
FF FF FF FF <09><8 байт нулей>
FF FF FF FE <09><8 байт нулей>
```
(`0xFF` никогда не встречается как первый байт настоящего ASCII-тега — по нему безопасно определять
конец списка).

## 3. LWRP (Livewire Routing Protocol) — задокументировано публично, для дозаполнения имён

Advertisement называет не все каналы (часть устройств шлёт только номер, без `PSNM` — раздел 2.4). Для
таких каналов используется второй, полноценно документированный (открытые рабочие реализации,
например `github.com/anthonyeden/Livewire-Routing-Protocol-Client`) протокол — **LWRP**, TCP порт 93.

**Подключение:** обычный TCP-сокет на `<IP узла>:93`. Аутентификация на уровне сокета не нужна —
опробовано и подтверждено на реальном узле (см. ниже), команда `SRC` отдаёт данные сразу после
подключения без какого-либо логина/пароля.

**Команды** — текстовые строки с `\n` в конце. Известный набор: `VER, IP, SET, SRC, DST, MTR, LVL,
GPI, GPO, MIX` (не все реализованы в этом проекте — см. раздел 5).

**Формат ответа на `SRC`** — блок `BEGIN...END`, внутри по одной строке на источник:
```
BEGIN
SRC 1 PSNM:"Novoe Expres" RTPE:0 RTPA:"239.192.0.1" INGN:-120 NCHN:2 RTPP:240 TXTO:250
SRC 2 PSNM:"DorogSAT" RTPE:0 RTPA:"239.192.0.2" INGN:-120 NCHN:2 RTPP:240 TXTO:250
...
SRC 10 PSNM:"" RTPE:0 RTPA:"239.192.0.10" INGN:-120 NCHN:2 RTPP:240 TXTO:250
...
END
```
(реальный ответ с узла `172.22.0.47:93`, PC с Axia «Livewire Windows Driver» — см. `VER` ниже).
Формат: `SRC <номер канала> <ТЕГ>:<значение> ...`, значения-строки в кавычках (могут быть пустыми —
`PSNM:""` у неиспользуемого слота 10 — это не ошибка парсинга, а «имя не задано»), значения-числа без
кавычек. Пробел внутри кавычек не разбивает токен (`PSNM:"Novoe Expres"` — один токен, не два).

Поля в `SRC`: `PSNM` — **имя канала** (то, что нужно), `RTPE` — включён ли источник (0/1), `RTPA` —
мультикаст-адрес того же канала (кросс-проверка, см. ниже), `INGN` — входной гейн, `NCHN` — число
каналов (2=стерео), `RTPP` — RTP payload type, `TXTO` — таймаут передачи.

**Формат ответа на `VER`** — одна строка, без `BEGIN/END`:
```
VER LWRP:1.2 DEVN:"lwwd" NSRC:24 NDST:24 NGPI:24 NGPO:24 SVER:1.2
```
`DEVN:"lwwd"` = «Livewire Windows Driver» — это ПК, а не физический узел, что объясняет, почему у него
через Advertisement `NUMS=0` (не рекламирует свои источники по мультикасту), но через LWRP отдаёт
полноценную таблицу из 24 именованных источников — LWRP-таблица узла не обязана совпадать с тем, что
физически им порождается: это скорее «известные этому софту источники» (в случае PC-логгера — его
собственный сконфигурированный список), а не только «мои собственные каналы».

**Формат ответа на `DST`** (получатели/назначения, не нужно для целей этого проекта, но замечено):
тот же `BEGIN...END`, поле имени называется `NAME` (не `PSNM`, в отличие от `SRC`!), адрес — `ADDR`.
Замечено: `ADDR` иногда содержит хвостовой мусор после самого адреса (`"239.192.16.207 <V-Mode 3>"`) —
надо быть готовым обрезать лишнее, если/когда этот путь будет реализован.

## 4. Как проверялось

- **PSID ⇔ FSID** (Advertisement): для каждого найденного источника значение `PSID` (int32) и значение
  `FSID`, интерпретированное как IPv4 `239.192.X.Y`, дают один и тот же номер канала по формуле
  `N = X*256 + Y` — проверено на всех источниках всех образцов, без единого расхождения.
- **HWID/INIP ⇔ реальный source IP пакета** (Advertisement): `HWID` (младшие 2 байта) и `INIP`
  (все 4 байта) во всех образцах совпадали с исходным IP-адресом отправителя пакета (из IP-заголовка) —
  подтверждает, что это поля "мой собственный адрес", а не что-то про адресуемый источник.
- **NUMS ⇔ количество `S0NN`-блоков** (Advertisement): совпадает во всех образцах.
- Пакет с `NUMS=0` (устройство `logger1` (ip-драйвер), IP `172.22.0.47`) не содержит ни одного
  `S0NN`-блока — подтверждает, что `NUMS=0` — нормальное, не ошибочное состояние.
- **SRC `<номер>` ⇔ RTPA** (LWRP): номер канала в `SRC <N>` совпадает с адресом в `RTPA`, декодированным
  по той же формуле `239.192.(N div 256).(N mod 256)` — проверено на реальном ответе с `172.22.0.47`
  (каналы 1..24, `RTPA` от `239.192.0.1` до `239.192.0.24` строго по порядку).

## 5. Реализация в этом проекте

- `Quince.Service/Audio/Livewire/LivewireAdvertisementParser.cs` — парсер Advertisement
  (`Parse(payload, now)`, возвращает список найденных источников, а не один — один пакет может
  описывать сразу много каналов).
- `Quince.Service/Audio/Livewire/LwrpParser.cs` — чистый парсер ответа `SRC` (`ParseSourceNames`).
- `Quince.Service/Audio/Livewire/LwrpClient.cs` — TCP-клиент LWRP (`QuerySourceNamesAsync`):
  подключается на `<IP>:93`, шлёт `SRC`, читает до `END`/таймаута (3с), в лучшем случае — узел просто
  не отвечает и результат пуст, никакого исключения наружу.
- `Quince.Service/Audio/Livewire/LivewireDiscoveryService.cs` — слушает мультикаст-группу
  Advertisement на выбранном в настройках интерфейсе; при первом пакете от нового IP один раз (не
  повторно — в README открытой реализации предупреждение, что частые подключения могут «плохо
  повлиять» на реальные устройства) запрашивает у него `SRC` через `LwrpClient` и дозаполняет имена
  каналов, которых не было в Advertisement — **никогда не перезаписывает** имя, которое уже пришло
  из Advertisement напрямую от исходного устройства (LWRP-таблица чужого узла может относиться к
  своему локальному списку, а не быть авторитетной для чужого канала).
- `Quince.Service.Tests/Audio/LivewireAdvertisementParserTests.cs`,
  `Quince.Service.Tests/Audio/LwrpParserTests.cs` — тесты на реальных данных из этого исследования.
- UI выбора канала — вкладка Livewire в `Pages/Shared/ChannelEditDialog.razor`.

## 6. Что осталось непонятным / не реализовано (не мешает работе, но на будущее)

- Advertisement: смысл `NEST`, `ADVT`, `TERM`, `INDI`, `ADVV`, `SHAB`, `FAST`, `FASM`, `BAST`, `BASM`,
  `STPL` — неизвестен (явно не номера каналов и не адреса — вероятно, флаги готовности/статуса линка,
  таймауты или внутренняя телеметрия устройства). Парсер их читает (чтобы корректно пропустить и не
  сбить смещение), но не интерпретирует.
- LWRP: команды `DST`/`VER`/`MTR`/`GPI`/`GPO`/`MIX`/`SET` не реализованы — только `SRC`, поскольку
  только он нужен для имён каналов-источников. `DST` (см. раздел 3) пригодился бы для мониторинга
  назначений, если это когда-нибудь понадобится.
- LWRP: не проверено поведение при действительно параллельных запросах к одному узлу, при обрыве
  соединения посреди `BEGIN...END`-блока, и при ответах, которые вообще не укладываются в `BEGIN/END`
  (кроме однострочного `VER`) — `LwrpClient` рассчитан быть терпимым (таймаут → что успело прийти),
  но по-настоящему стресс-тестирован не был.
